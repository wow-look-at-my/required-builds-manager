# Required Builds Manager

A Cloudflare Worker that acts as a GitHub App webhook handler. It listens for `status`, `check_run`, and `workflow_run` events, aggregates all build states for a commit, and publishes a single "all-builds" combined **commit status** using a low-water-mark algorithm (failure > pending > success). The status's `description` is a running count (e.g. `2/3 builds passed`, or `1/3 builds failed`) that updates as builds finish, and its `target_url` ("Details" link) points at a **self-hosted breakdown page** the worker serves, which breaks every build into Failed/In progress/Passed sections — each build a link to its check, with per-step state — naming which failed (on failure the passing builds are omitted to keep focus on what's broken). A commit status is used instead of a check run because **GitHub freezes a `completed` check run** — a later PATCH can't move it back to `in_progress` — so a check run that went green (even prematurely, before all builds registered) stayed green and kept merge unblocked; a commit status has no such freeze (GitHub keeps the latest per context and lets it move success/pending/failure freely on every event). To stop GitHub native auto-merge from irreversibly consuming a *transient* green (an all-green subset before stragglers register — the PazerOP/scratch#117 incident), a computed `success` is held behind a **green-settle window**: the worker publishes `pending` and only promotes to `success` after it stays green, with an unchanged build roster, for `GREEN_SETTLE_MS` (default 45s); `failure`/`pending` are never delayed. Listening for `workflow_run` lets it catch `startup_failure` (e.g. invalid workflow YAML), which produces no statuses or check runs and would otherwise be invisible. It also gates **pull-request merges** on the same `all-builds` result *without* a required status check (which would block pushes): on `pull_request` events — and as builds finish — it converts a PR to **draft** while `all-builds` isn't settled-green and marks it ready once it is, so a PR can't be merged until CI passes while direct `git push` stays completely unaffected. This gate is best-effort, not loophole-proof against an adversary (a regression-window race exists), and is intended for trusted, non-adversarial repos.

Publishing a commit status requires the GitHub App to hold the `Commit statuses: write` permission (it also needs `Checks: read`, `Actions: read`, `Contents: read` to *read* the builds it aggregates). The PR merge-gate additionally needs **`Pull requests: write`** (to flip a PR between draft and ready) and the App must be **subscribed to the `pull_request` webhook event**. It no longer needs `Checks: write`. `WEBHOOK_SECRET` doubles as the HMAC key that signs the breakdown page's capability URLs.

## Tech Stack

- **Runtime**: Cloudflare Workers (ESNext, no Node.js APIs) + one Durable Object (`CheckRunPublisher`) used as a per-commit serialization lock + self-heal alarm
- **Language**: TypeScript 5 with strict mode
- **Build/Deploy**: Wrangler 4
- **Testing**: Vitest 3 with `@cloudflare/vitest-pool-workers` (runs tests inside the Workers runtime)
- **Crypto**: Web Crypto API only — no external crypto libraries
- **Dependencies**: Single production dependency (`yaml` for config parsing); rest are devDependencies

## Architecture

### Webhook Flow

1. Receive POST from GitHub (`x-github-event: status`, `check_run`, `workflow_run`, or `pull_request`)
2. Verify HMAC-SHA256 signature (`x-hub-signature-256` header)
3. Parse event, extract SHA/state/context/repo (workflow-run name may be null → treated as empty context)
4. Authenticate as GitHub App: generate JWT → exchange for installation token (cached in KV + in-memory with 5-min threshold)
5. Fetch per-repo config from `.github/required-builds.yml` (falls back to org `.github` repo, then defaults)
6. Loop prevention: skip a `status` event whose context matches the configured name (that's our own published all-builds status), and skip a `check_run` event from our own `app.id` (a leftover all-builds check run from before the switch)
7. Aggregate: fetch all statuses + check-runs + workflow-runs for the SHA, deduplicate by context/name, filter out ignored patterns, collect each build's name/kind/state/detail/url/timing, fold in the triggering event **unless it's pending** (a pending incoming is dropped — the deduped listing is already authoritative for every build's success/pending state, so trusting one only risks wedging `all-builds` on "in progress"; a failure or success incoming is still folded for correctness under list-endpoint lag), and compute the combined state + the structured per-build breakdown (title + grouped failed/pending/passed entries). Per-step detail (which step of a job failed/is running) is NOT fetched here — it's deferred to `enrichWithSteps`, which the breakdown page calls on render, so the hot webhook path makes no `getWorkflowJob` call per job
8. Publish the combined **commit status** using the configured context (`state` is success/pending/failure/error; `description` is the running count like `2/3 builds passed`; `target_url` is the capability URL to the self-hosted breakdown page), routed through the per-commit Durable Object (`publishViaCoordinator` → `CheckRunPublisher` → `publishStatus`). GitHub upserts statuses by context, so re-posting just updates the single `all-builds` status for the commit — no find-or-create, no duplicates. The DO also **debounces** two ways: (a) dedup — if the new `{state, description, target_url}` is identical to the last one it successfully published, it skips the POST entirely (each POST would otherwise create a new status object and fire a fresh `status` webhook, flooding PR subscribers with duplicate notifications); and (b) a time-based **leading-edge throttle** — the first publish in a quiet window goes out immediately, but rapid follow-ups within `PUBLISH_DEBOUNCE_MS` (1000ms) are coalesced into a single trailing flush driven by the alarm, so a burst of distinct counts doesn't fire a notification per tick. A `pending` aggregate arms the self-heal alarm; failure/error are terminal and clear it. A computed `success` is **held**, not published immediately — the DO publishes `pending` and arms a green-settle window (see Key Design Decisions); only the alarm promotes it to `success` once it has stayed green, with no new build registering, for the window, so a transient green can't be consumed by auto-merge

### Key Design Decisions

- **Token caching**: Installation tokens cached in Cloudflare KV (shared across all isolates) with in-memory fallback. KV is optional — if not bound, falls back to per-isolate in-memory cache only
- **Retry with backoff**: All GitHub API calls use `fetchWithRetry` (3 retries, exponential backoff) for transient 5xx/429/network errors
- **Per-repo config**: `.github/required-builds.yml` supports custom context name and ignore patterns (glob); falls back to org `.github` repo, then defaults
- **Output is a commit status, not a check run**: GitHub **freezes a `completed` check run** — once published with a conclusion, a PATCH can't move it back to `in_progress` (it updates the output text but keeps the frozen status/conclusion). So a check run that went green — including prematurely, before all builds registered — stayed green and kept merge unblocked (observed: a `completed/success` run with a "3/5 builds passed -- In progress (2)" body and a `completed_at` that predated its `started_at`). A commit status has no terminal freeze: GitHub keeps the latest status per `context` and lets it move success/pending/failure on every event, so `all-builds` always reflects the current aggregate (and can return to pending/failure if a new build appears for an already-green commit). `publishStatus` POSTs `{state, context, description, target_url}`. Because a status `description` is capped at ~140 chars, the full per-build breakdown lives on a self-hosted page (see next), linked via `target_url`; the description is just the running count (`{passed}/{total} builds passed`, or `{failed}/{total} builds failed` on any failure — it updates as builds finish, since every event re-aggregates).
- **Green-settle window (transient-green / auto-merge guard)**: a moving commit status fixes a *stuck* premature green, but NOT a *transient* one — GitHub native auto-merge consumes a required check the instant it goes green, and that merge is irreversible. `computeAllBuildsState`'s low-water-mark can only see builds that have ALREADY registered, so right after a push (notably an `update-branch` merge commit) a green SUBSET can register before the builds that will fail have created their check runs, and the aggregate momentarily reads all-green → `success`. Auto-merge then merges a PR whose CI ultimately fails (the PazerOP/scratch#117 incident: a non-monotonic `pending → success → pending → failure` status history, merged inside the transient-`success` window). The fix lives entirely in the `CheckRunPublisher` DO (`applyGreenSettle`): a computed `success` is NEVER published on the leading edge. Instead the DO publishes `pending` and opens a settle window (`GREEN_SETTLE_MS`, default 45s); the existing reconcile alarm fires at the window deadline, re-aggregates, and publishes `success` only if it is STILL success AND no NEW build registered during the window (a brand-new build identity — the telltale that more builds were still coming — restarts the clock). The restart trigger is specifically a new `kind:name` identity, NOT any roster difference: GitHub's list endpoints are eventually consistent, so a build already seen green can drop out of one re-aggregation and reappear in the next, shrinking then growing the roster with no actual new build. The window remembers the **union** (high-water mark) of every identity seen green and restarts only on one absent from it — so a shrink, or a known build flapping back in, never resets the clock. (Without this, list-lag flapping kept `all-builds` stuck on `pending` for ~90s with every build green — the wow-look-at-my/ai-shadertoy#4 incident: an exact-roster-equality check restarted the 45s window every time a build flapped out and back.) Only `success` is delayed; `failure`/`pending` publish immediately (they're responsive and can never cause a bad merge). `computeAllBuildsState` is intentionally NOT changed (it has no expected-build roster, so it cannot itself distinguish "all passed" from "the subset that registered passed" — and adding a cross-commit expected-set floor was rejected as the riskier mechanism: it needs per-repo+branch persistence and reliable branch attribution from `status` payloads, and a stale roster would over-block the merge gate far worse than a ~45s settle delay). `index.ts` passes the roster (`kind:name` of every aggregated build) to the DO so the leading edge and the alarm share the same "did a new build appear?" signal.
- **Self-hosted breakdown page (capability URL)**: the status's `target_url` points at `GET /b/{owner}/{repo}/{sha}?k=<sig>`, served by the worker. On a GET it re-aggregates live and renders an HTML page (`render.ts`) grouping builds into Failed/In progress/Passed — each linked to its check, with per-step state and a total-time line — the same job/step structure GitHub's run view shows, but **no logs**. `<sig> = HMAC-SHA256(WEBHOOK_SECRET, "{owner}/{repo}/{sha}")` (`sign.ts`); the worker verifies it (constant-time) and 404s otherwise (never revealing whether the repo/sha exists). The signature IS the access control: GitHub only reveals a private repo's status — and thus this URL — to users with read access, so holding a valid URL means you were shown it; the signature stops anyone *guessing* the URL for a repo/sha they can't see. Trade-off: it's a capability URL — anyone the link is shared with can view, and access isn't revoked when someone loses repo access (acceptable since the page shows only build/step state, never logs). Served with `Referrer-Policy: no-referrer` + `Cache-Control: no-store` so the secret doesn't leak via referer/caches. HTML-escaped, and only http(s) build URLs become links (no `javascript:`). The aggregate also exposes the earliest build start for the page's `Total time` line (earliest start → latest finish).
- **Fail closed on an empty aggregate**: an aggregate with zero relevant builds is reported as `pending`, never `success`. At the very start of CI the statuses/check-runs listings are momentarily empty (a job has fired a webhook but not yet registered its check run); reporting `success` there marks the combined result green before a single build has run. The one exception is when builds did report but were all excluded by ignore patterns (or the triggering event itself is ignored) — then there is genuinely nothing to wait for and `success` is correct.
- **No failure short-circuit**: Every event runs the full aggregation (the old "incoming failure → short-circuit without fetching" path was removed) so the breakdown always reflects all builds. The triggering event is still folded in for correctness under list-endpoint lag, but **never when it's pending** — the deduped listing is authoritative for every build's success/pending state, so folding in a pending incoming adds nothing and can only invent or regress state. (Before this guard, a pending `workflow_run` event pushed a phantom "in progress" row — passing/running workflows have no standalone row, only failing ones do — and a stale or redelivered pending status/check event could drag an already-passed build back down via the low-water-mark; either one wedged `all-builds` on "in progress" while every real build was green, because the stale pending event was the last one processed and nothing re-aggregated to undo it.) A failure incoming is still folded (the `startup_failure`-under-lag case) and so is a success (harmless: it can only add or keep a passed row for the build that just reported, never raise or wedge anything).
- **Single status, upserted by context**: GitHub collapses commit statuses by `context` and uses the most recent per context, so re-posting the `all-builds` status just updates the one entry for the commit — no find-or-create, no duplicates (the hazard that forced check runs to be PATCHed in place). The latest status per context is also what branch-protection required checks evaluate.
- **Per-commit serialization (Durable Object)**: statuses upsert by context so duplicates aren't a hazard, but concurrent events for one SHA can still interleave their fetch+POST so an earlier-aggregated state lands last, leaving a stale status. Every publish is routed through the `CheckRunPublisher` Durable Object, keyed by `owner/repo@sha`, which wraps publish in `ctx.blockConcurrencyWhile` so events for one commit run one-at-a-time (last to arrive wins). Declared in `wrangler.jsonc` as a `new_sqlite_classes` migration (works on the Workers free plan too).
- **Self-heal / reconciliation (Durable Object alarm)**: the worker is otherwise purely event-driven, so if the terminal event is dropped, reordered behind a stale event, or its publish fails transiently, the status would freeze on "pending" forever. Whenever a *pending* result is published the DO arms an `alarm`; when it fires it mints a fresh token, re-aggregates from the authoritative listing (no incoming event — nothing is folded in), and re-publishes the status (reusing the stored capability `target_url`). It re-arms with exponential backoff (30s -> 5min cap, ~12 attempts) while still pending and cancels itself once terminal. The DO persists a small `reconcile` record (owner/repo/sha/installationId/appId/context/ignore/targetUrl/attempts) only while non-terminal; on resolution it's deleted. (A status isn't *frozen* once terminal like a check run, but a never-arriving terminal event still needs the alarm to drive it off "pending".) This same alarm + re-aggregation machinery also drives the **green-settle** confirmation (see above): a held green arms the alarm at the settle-window deadline (not the backoff schedule, and it doesn't count against the attempts cap), and the alarm's re-aggregation goes through `applyGreenSettle` too, so it can never publish an unconfirmed success either.
- **Repost debounce (Durable Object)**: a commit with many builds fires a torrent of events, most of which don't change the aggregate (one build finishing while others run leaves `2/29 builds failed` unchanged). Reposting an identical commit status is **not** a no-op on GitHub's side — statuses are append-only per `context`, so every POST creates a *new* status object and fires a fresh `status` webhook, which floods anyone subscribed to the PR with duplicate "all-builds failed" notifications. So the DO records the last *successfully* published `{state, description, targetUrl}` (in DO storage, keyed per commit) and **skips the POST when the next publish is identical** — both on the event path and in the reconcile alarm. It records only *after* a successful POST, so a dropped/failed publish is never mistaken for "already sent" (the 403 retry and the alarm still re-attempt it); and because an equal record means GitHub provably already has that status, the alarm can safely skip an unchanged-but-still-pending re-publish while continuing to re-check for the missed transition. Any genuine change (the count ticks, or the state flips) still publishes immediately — no added latency. The `lastPublished` record persists past the terminal state on purpose: the flood is largely *terminal* events (a failure re-reported as more builds finish), so it must stay to debounce those too.
- **Time-based debounce / throttle (Durable Object)**: dedup above kills *identical* reposts; this additionally coalesces a burst of *distinct* updates (a matrix ticking `1/29 → 2/29 → 3/29 builds failed` within a second) so the worker publishes at most once per `PUBLISH_DEBOUNCE_MS` (1000ms) window. It's a **leading-edge throttle**: the first event in a quiet window publishes *immediately* (the merge gate stays responsive — no second of latency on the first state), and any events arriving within the window are stashed in a `pendingPublish` record and emitted by a single **trailing flush** driven by the DO `alarm`. The flush re-mints its own token (with the same 403-refresh retry as the leading path) and runs the same `doPublish` (so `lastPublished` dedup still applies — a burst that nets out to no change posts *nothing*). The flush alarm is always sooner than any reconcile alarm, so when both are due the alarm services the flush first, then `doPublish` re-arms reconcile as needed. `doPublish` arms the reconcile alarm *before* every publish (pending or terminal) and clears it only after a terminal publish lands, so a failed publish — leading or flushed, pending or terminal — is always retried by the self-heal alarm. Window latency (≤1s) is irrelevant to CI but sharply cuts the `status` webhooks a large matrix produces. `index.ts` is unchanged — the throttle lives entirely in the DO.
- **Stale-token 403 recovery**: installation tokens bake in the installation's permissions *at mint time*, and tokens are cached in KV for ~1h. So right after `statuses:write` is approved, a cached token still 403s on publish (reads, which it already had, keep working). On a 403 the publish path force-refreshes the token (`getInstallationToken(..., forceRefresh=true)`, bypassing both caches) and retries once; the reconcile alarm does the same. A 403 that survives a fresh token is a real permission problem and is not retried further. `publishStatus` attaches the HTTP `status` to thrown errors so callers can make this distinction.
- **Per-step breakdown (lazy, breakdown-page only)**: for a check run that *failed* or is *in progress* (passed jobs collapse to a single line), `enrichWithSteps` parses the Actions job id from the check run's URL (`.../job/<id>`) and calls `getWorkflowJob` to fetch that job's steps, then attaches them to the build (passed/failed/running/queued/skipped) — so the breakdown page shows exactly which step failed or is running. This is a SEPARATE pass from `computeAllBuildsState`, invoked ONLY when the breakdown page is rendered (`GET /b/...`), never on the webhook path: it costs one `getWorkflowJob` call per failed/in-progress Actions job, and the published commit status needs only state + title, so doing it on every webhook would spend an API call per job on data the publish path discards. The breakdown page is human-triggered and rare, so that per-job cost lands only when someone views the detail. Best-effort: external (non-Actions) check runs whose URLs don't match, and any fetch failure, simply get no step detail. Requires `actions:read`.
- **Dashboard auth (GitHub OAuth; public needs no login)**: `/dashboard` shows public-repo stats to everyone with NO login prompt (200, just an optional "Sign in with GitHub" link); signing in only ADDS the private repos that user can access. Sign-in is a user-to-server OAuth flow: `/dashboard/login` → GitHub authorize (with a signed, short-lived CSRF `state` cookie) → `/dashboard/callback`, which verifies the state, exchanges the code for a one-time user token, lists which tracked private repos that token can read (`GET /repos/{o}/{r}`), bakes that allow-list into an HMAC-signed session cookie, and discards the token (never stored). Rendering filters private repos/receipts to that allow-list (`filterSummaryForViewer`) and recomputes totals. Needs `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`; unset → public-only. The App must register `{origin}/dashboard/callback` as an OAuth callback URL.
- **Infinite loop prevention**: our own published `all-builds` **status** fires a `status` event; `index.ts` skips any `status` event whose context matches the configured name. We no longer publish check runs, so the `check_run` self-loop guard (matching `check_run.app.id` against the App's id) now only filters out a leftover all-builds check run from before the switch (aggregation filters those from the listing by the same `appId`). The PR merge-gate's own draft/ready toggles fire `pull_request` events back at the worker, but `maybeGatePrs` is idempotent (it skips a PR already in the desired state), so those re-entrant events no-op rather than loop.
- **PR merge-gate (draft toggling, not a required check)**: GitHub's only native CI merge-gate is a *required status check*, which is attached to the branch ref and therefore also blocks direct `git push` of un-checked commits (the merge button and a push are the same ref update to it). To gate PR merges on `all-builds` *without* touching pushes, the worker instead toggles a PR's **draft** state (a draft PR can't be merged). On a `pull_request` event (routed with `force=true`) and after each publish, `maybeGatePrs` drafts any open PR whose head's `all-builds` isn't *confirmed* green (green-settle terminal `success`) and marks it ready once it is. A held/unconfirmed green is a **no-op** (returns without touching PRs), so a transient green never releases a merge and an already-released PR never flaps back to draft on a re-aggregation. It only marks-ready PRs **it drafted** (tracked per-commit in DO storage as `draftedPrs`), so an author's own WIP draft is never force-readied; and it only makes PR API calls when a `pull_request` event forces it or after a PR has already been seen for the commit (`hasPrs`), so the hot path for the many non-PR commits makes no PR calls at all. This is **best-effort, not loophole-proof**: a regression landing in the brief window between green and re-draft could still be merged — acceptable for trusted, non-adversarial repos (the chosen trade-off to keep pushes free). Requires `Pull requests: write` and the `pull_request` webhook subscription. (The native alternative — making `all-builds` a required status check — is loophole-proof but blocks pushes, so it's only suitable scoped to integration branches you merge into.)
- **Deduplication**: Statuses deduplicated by `context`, check-runs and workflow-runs by `name` (API returns newest first)
- **Check-run mapping**: `queued`/`in_progress` → pending; completed with `success`/`neutral`/`skipped` → success; `failure`/`timed_out`/`cancelled`/`action_required` → failure; `stale` → pending
- **Startup-failure detection**: A `startup_failure` workflow run (e.g. invalid workflow YAML) creates NO check runs or statuses, so it's invisible to `listStatuses`/`listCheckRuns`. Aggregation also calls `listWorkflowRuns(head_sha)` and folds any failure-concluding workflow run (notably `startup_failure`) into the low-water-mark — so a broken workflow blocks `all-builds` and, because aggregation re-queries on every event, the failure persists even when a later passing build re-triggers aggregation. The fetch is best-effort: if it fails (e.g. the app lacks `actions:read`, or Actions is disabled), it degrades to `[]` rather than erroring the whole aggregation. Only failure-concluding runs are added; passing/pending workflows are already represented by their own check runs. The validation text for a `startup_failure` (the "Invalid workflow file..." message) is NOT exposed via the REST/GraphQL API — only GitHub's web UI — so the breakdown surfaces the conclusion (`startup_failure`) and links to the run's `html_url`, where the full message renders.
- **PKCS#1 support**: Manually wraps PKCS#1 RSA keys in PKCS#8 DER envelope for Web Crypto compatibility

## Environment Variables

Set as Cloudflare Worker secrets (never commit these):

| Variable | Description |
|---|---|
| `GITHUB_APP_ID` | GitHub App identifier |
| `GITHUB_APP_PRIVATE_KEY` | PEM-encoded RSA private key (PKCS#1 or PKCS#8) |
| `WEBHOOK_SECRET` | GitHub webhook HMAC secret — also the HMAC key for signing the breakdown page's capability URLs AND the `/dashboard` OAuth session/state cookies |
| `GITHUB_CLIENT_ID` | Optional. The GitHub App's OAuth client ID, enabling "Sign in with GitHub" on `/dashboard` so a signed-in user also sees the private repos their account can access. |
| `GITHUB_CLIENT_SECRET` | Optional. The GitHub App's OAuth client secret (pairs with `GITHUB_CLIENT_ID`). When either is unset, the dashboard is public-only (no sign-in). |
| `GREEN_SETTLE_MS` | Optional (not secret — a plain var). Milliseconds a computed `success` must stay green, with no new build registering, before it's published (the green-settle window; default 45000). Only the `success` transition is delayed; `failure`/`pending` publish immediately. Set `0` to confirm on the next re-aggregation rather than waiting the wall-clock window (a leading-edge success is still never published directly). |

## Testing

Tests run inside the Cloudflare Workers runtime via `@cloudflare/vitest-pool-workers`. Test bindings are configured in `vitest.config.ts` with dummy values.

```bash
npm test                    # Run all tests
npx vitest run test/aggregate.test.ts  # Run a single test file
```

**Testing patterns used:**
- `vi.mock()` for module mocking (e.g., `./github`, `./auth`, `./verify`, `./config`, `./sign`, `./render`)
- `fetchMock` from `cloudflare:test` for HTTP request mocking
- `beforeEach` resets mocks between tests
- Tests cover happy paths, error cases, deduplication, and state transitions

## CI/CD

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and **only does checks, not deploys**:

1. `npm ci` — clean install
2. `npx tsc --noEmit` — type checking
3. `npx vitest run` — tests

Node.js 22 is used in CI. Deploys happen separately via Cloudflare's GitHub integration (see Deployment section above).

## Code Conventions

- No ESLint/Prettier config — use tabs for indentation (matching existing code)
- Named exports for functions, default export for the Worker handler in `index.ts`
- Interfaces defined at module level, co-located with usage
- No `any` types in core logic — strict TypeScript throughout
- Pagination via infinite `for (;;)` loop with break conditions
- Errors thrown as `new Error(...)` with descriptive messages
